\section{Introduction}

Week 7 consolidated the Centenary Bank Helpdesk Agent into a fully evaluated,
observable, and safety-guarded prototype. Building on the persistent-memory
agentic loop from Week 6, this week delivered four interconnected deliverables:
a 30-scenario evaluation set, a structured observability trace bundle, a
failure catalogue, and a dedicated guardrail implementation module with
evidence. Together they demonstrate that the agent can be evaluated
systematically, that every decision is fully auditable, and that explicit,
testable safety controls are in place.

% ---------------------------------------------------------------------------
\section{Evaluation Framework}

A formal evaluation set of 30 scenarios was designed across six categories,
with five cases each. Each scenario specifies the user request, expected
behaviour, correct tool path, and any safety flags to be recorded.
The evaluation harness (\texttt{week7\_evaluation\_harness.py}) executes the
real Week~6 controller against all scenarios using a scripted planner.
Six metrics are assessed per run: task completion, groundedness, tool
selection, instruction following, latency, and safety violations.
Latency budgets are 3\,000\,ms (direct answer), 8\,000\,ms (tool call),
and 12\,000\,ms (failure recovery).

\section{Observability and Tracing}

Every run emits a structured trace stored in
\texttt{evidence/traces/week7/week7-observability-evidence.json}.
Each record captures: the prompt template ID and SHA-256 hash (so any change
between runs is detectable); the retrieval query, source IDs, and relevance
scores; the tool name, redacted arguments, status, and error type;
per-iteration planning latency and total end-to-end latency; the terminal
outcome label (e.g.\ \texttt{TICKET\_CREATED}); and safety flags emitted
when a guardrail fires. The design satisfies the requirement that any run can
be reconstructed offline without console output, enabling retrospective audits
and regression testing.

\section{Guardrail Implementation}

\subsection{Motivation}

The Week~6 controller contained safety controls embedded inline across its
planning, tool-execution, and observation steps. While effective, these controls
were implicit and scattered. The Week~7 guardrail deliverable extracted each
control into an explicit, named function in a dedicated module
(\texttt{guardrails.py}), making every check independently callable,
auditable by name, and testable in isolation without running the full agent.

\subsection{Test Evidence}

A demo script (\texttt{demo\_guardrails.py}) runs 27 test cases covering both
the safe-pass and unsafe-block paths for every guardrail. Results are written
to \texttt{evidence/traces/week7/guardrail-evidence.json}, recording the
guardrail ID, test input, trigger result, safety flag, and reason string for
each case. All 27 cases passed with zero failures. Key properties verified:
no action or tool executes outside the approved sets (G-01, G-03); the model
cannot inject or forge identity fields (G-02); no factual answer is produced
without retrieved evidence, preventing fabricated bank policies (G-04); prior
case memory does not substitute for human approval of escalation (G-05,
G-06); and prompt injection attempts and out-of-scope financial actions are
blocked at input classification (G-08, G-09).

\section{Conclusion}

Week~7 brought the prototype to a state where its behaviour is evaluable
against a defined scenario set, its decisions are fully traceable, known
failure modes are catalogued and remediated, and its safety controls are
named, implemented, and independently verified. All acceptance criteria were
met: 30 evaluation scenarios executed and recorded, five failure cases
remediated and re-tested as pass, and 27 guardrail test cases all passing
with zero safety violations. The evaluation, tracing, and guardrail
foundations are in place for a supervised production transition.
